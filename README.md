# 报价流水 API（商品调价 + 按月分区）

报价团队按 **UTC 自然月** 保管商品调价流水。月分区还没建时，流水先写入
`price_changes` 的默认分区 `price_changes_default`；需要时可为指定月份
**原子补建**月分区，把当月旧流水全部迁入，其他月份留在原处。

同时保留原有的只读查询与守护连接池能力（见文末“只读查询 API”）：查询走
只读连接池，录入调价与分区维护走独立的写连接池。

## 快速开始

```bash
docker compose up --build
```

- API 文档（Swagger UI）：http://localhost:8000/docs
- PostgreSQL：`localhost:5432`，用户/密码/库均为 `app`/`app`/`demo`
- `db/init.sql` 灌 `items` 种子数据，`db/schema.sql` 建调价流水父表、
  索引与默认分区；API 启动时也会执行一次 `db/schema.sql` 兜底。

## 数据模型

```sql
price_changes (
    id         bigint GENERATED BY DEFAULT AS IDENTITY,
    item_id    integer NOT NULL REFERENCES items(id),   -- 沿用现有商品编号
    changed_at timestamptz NOT NULL,                    -- 调价时间
    new_price  numeric(10,2) NOT NULL CHECK (new_price > 0),
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (id, changed_at)
) PARTITION BY RANGE (changed_at);
```

- 分区名固定为 `price_changes_YYYYMM`，范围是该 UTC 月的 `[月初, 下月初)`。
- 主键必须包含分区键；`id` 由父表 identity 统一发号。补建迁移时连同原
  `id` 一起搬运，**不会重新编号**。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/price-changes` | 录入一条调价流水：`item_id`、`changed_at`（带时区）、`new_price`；响应的 `partition` 是实际落入的分区 |
| GET | `/price-changes?month=YYYY-MM` | 按 UTC 月查流水，每行带 `partition`（所在分区） |
| GET | `/partitions` | 列出全部分区（含默认分区及其边界） |
| POST | `/partitions/{month}/backfill` | 补建该月分区并迁移当月旧流水 |
| GET | `/pool/stats` | 只读连接池指标 |
| POST | `/query/normal`、`/query/slow`、`/query/error` | 原有演示接口 |

### 在 /docs 里演示

1. **写入默认分区**：`POST /price-changes`，
   `{"item_id":1,"changed_at":"2026-11-20T10:00:00Z","new_price":"9.99"}`，
   响应 `partition` 应为 `price_changes_default`。
2. **按月查询**：`GET /price-changes?month=2026-11`，每行 `partition`
   显示当时所在分区。
3. **补建分区**：`POST /partitions/2026-11/backfill`，响应
   `created=true`、`migrated_rows` 为迁移行数；随后再查 `2026-11`，
   这些行的 `partition` 变为 `price_changes_202611`。
4. **幂等**：重复调用同一路径，响应 `created=false`，不会再建分区。
5. **其他月份不动**：`2026-12` 等月份的旧流水仍在
   `price_changes_default`。
6. **失败不影响原状**：用 `?lock_timeout=1s` 在父表被长事务锁住时调用，
   返回 `503`，当月流水与分区路由保持原样；锁释放后重试即可成功。

### 状态码

`200` 成功；`400` 月份格式非法；`404` 商品编号不存在；`409` 该月已被
另一个名字的分区覆盖；`422` 请求体校验失败；`503` 补建等锁超时；
`500` 补建事务失败（均已回滚）。

## 分区补建的语义与保证

- **原子**：清空默认分区中的当月行 → 建月分区 → 把暂存行（含原 `id`）
  写回，全部在**一个事务**内完成，提交前对外不可见。
- **不丢不重**：补建期间对父表取 `ACCESS EXCLUSIVE` 锁。直接写父表的
  请求会短暂等锁；PostgreSQL 会在锁释放后按新分区重新路由，因此
  已提交流水既不会丢，也不会同时出现在默认分区和新分区。
- **幂等**：同一月份的并发补建由事务级 advisory lock 串行化，后到者
  在锁内复查，发现分区已存在即返回 `created=false`。
- **可回滚**：等锁超时（`lock_timeout`，默认 2s）或迁移失败时事务整体
  回滚，旧流水仍在默认分区、月分区不存在，分区路由不变。
- **默认分区永远保留**：补建只迁移目标月份的旧行。

## 只读查询 API（带守护的 PostgreSQL 连接池）

数据库值班场景：多个应用共用有限的 PostgreSQL 连接。客户端等慢 SQL 超时后，
查询可能仍占着会话；未清理的事务也可能影响下一个请求。本服务用
FastAPI + 自研异步连接池解决这些问题：

- 每个请求可**分别设置**“等待连接的超时”（`acquire_timeout`）和
  “执行查询的超时”（`query_timeout`）；
- 排队中的请求被取消后**立即释放队列名额**（排队不占用连接）；
- 查询超时、客户端断开、SQL 报错后，连接标记为“脏”，**在确认会话
  状态已清理之前绝不再借出**：先做服务端取消（`pg_cancel_backend` 等价的
  CancelRequest）、回滚遗留事务、再用 `SELECT 1` 验证；无法确认的一律
  **关闭并更换新连接**；
- 连接数有硬上限：每条连接始终属于一个槽位，更换时先关旧再开新，
  取消与归还交错也不会越限；
- 会话级只读（`default_transaction_read_only=on`），查询池只跑固定的
  SELECT；调价录入与分区维护由独立的写池执行（`WRITE_POOL_SIZE`，默认 2）。

查询类接口（`/query/*`）的请求体都支持 `acquire_timeout` / `query_timeout`
（秒，`null` 表示不限）；`/price-changes` 与补建接口同样支持这两个查询参数。
响应码约定：`200` 成功；`503` 等连接/等锁超时；`504` 查询执行超时；
`400` SQL 错误；`502` 连接级故障；`499` 客户端中途断开。

## 关键设计

- **槽位模型**：池大小固定，每条连接处于 `idle / in_use / cleaning`
  三态之一；更换连接时先关闭旧连接再创建新连接，因此打开的连接数
  永远不会超过上限。
- **排队不持名额**：`acquire()` 的等待者只挂在条件变量上，被取消
  （如客户端断开）时从队列移除即可，不会泄漏连接。
- **脏连接不出借**：归还时若连接可能仍在执行查询（超时/断开）或
  刚发生 SQL 错误，则转入后台清理：先发服务端取消并等待查询任务
  收尾，再回滚遗留事务，最后 `SELECT 1` 验证会话空闲；任何一步失败
  即关闭并新建连接顶替。清理期间该槽位不可借出。
- **借出前把关**：借出时先做本地状态检查；空闲超过
  `checkout_verify_after` 秒（默认 10）的连接额外做一次 `SELECT 1`
  活性验证，防止数据库重启后把已死的空闲连接借给请求。

## 已知限制

- 连接关闭失败（如对端无响应且超时）时，客户端按已关闭记账，服务端
  可能短暂残留连接，依赖 PostgreSQL 的 TCP keepalive 最终回收；
  `/pool/stats` 的 `opened_connections` 是客户端视角。
- 排队唤醒不保证严格 FIFO（`asyncio.Condition` 语义），极端情况下
  可能有请求等待偏久，但都会在自己的 `acquire_timeout` 内得到确定结果。
- 单进程单事件循环；多副本部署时每个进程各有自己的连接池，
  总连接数 = 副本数 × `POOL_SIZE`，需要值班员按此规划。
- 活性验证只在“借出时”进行；验证通过与实际执行之间的极短窗口内
  连接仍可能失效（此时该请求报错、连接被更换，属正常兜底路径）。
